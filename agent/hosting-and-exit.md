# Hosting, and how to leave

Written 11 October 2026 on Jordan's request, after he asked whether Netlify is the right host once the site is public and promoted. Facts about this repository were read in it on that date. Statements about other hosts (Cloudflare, Vercel) are from general knowledge, not checked here, and are marked. What I could not see (Netlify's dashboard, plan, usage, pricing) is listed under "Not known". Prices and plan limits are deliberately not quoted: they change, and I cannot check them from here.

## Answer

Netlify is a reasonable host for this site. It is a statically generated site (`NITRO_PRESET = "static"`, publish directory `.output/public`, 82 MB by `du -sh` on a local build on 11 October) with two small edge functions. The Netlify-specific part is small and listed below, so leaving later is a known-size job. The risks are mostly about the account and the plan, not the technology.

## What is Netlify-specific

| What | Where | What it does | Portable? |
|---|---|---|---|
| Build settings | `netlify.toml` `[build]` | `npm run build:search`, publish `.output/public`, `NODE_VERSION = "20"`, `NITRO_PRESET = "static"` | Any CI or host with a Node build step. Nothing here is special. |
| Response header | `netlify.toml` `[[headers]]` | `X-Robots-Tag: noindex, nofollow, noarchive` on every path. **Must go before launch** (see below). | Every host can set a header. |
| One redirect | `netlify.toml` `[[redirects]]` | `/archive` to `/community/newsletter`, 301 | Yes. Also read by `scripts/check-links.mjs`. |
| Legacy redirects | `public/_redirects` (337 lines, 321 of them rules, generated by `scripts/parity/redirects.mjs`, checked by `scripts/check-redirects.mjs`) | Old www.cuahsi.org paths to their new pages | The `_redirects` format is Netlify's. (From general knowledge, not checked: Cloudflare Pages reads the same format.) Other hosts need the generator to write their own format (the script is the only thing to change). |
| `/api/geo` | `netlify/edge-functions/geo.ts` | Returns country and a position rounded to 0.1 degree, from Netlify's IP lookup (`context.geo`) | The file is 13 lines. The data source is host-specific (from general knowledge, not checked: Cloudflare gives country and coordinates in `request.cf`, Vercel in headers). A host with neither needs a geo-IP database. If this function is lost the card falls back to the visitor's time zone, then a default gage. |
| `/api/gage` | `netlify/edge-functions/gage.ts` | Asks USGS with the API key and asks the CDN to cache the answers (only partly effective, item 6 below) | Uses `Netlify.env` for the key and `Netlify-CDN-Cache-Control` for caching. Both have equivalents elsewhere, but the file is 90 lines with real logic (validation, three request kinds, cache times that adapt to USGS's remaining allowance), so leaving means a careful rewrite and a re-test of its behaviour (including whatever caching the new host gives) on the new host, not a quick port. If lost, the card asks USGS directly from the browser, without the key and at USGS's lower limit (`usgsGet` in `composables/useGageCard.ts` does this today when the function is absent). |
| Environment variable | Netlify dashboard | `USGS_API_KEY`, scopes Builds, Functions, Runtime, three deploy contexts (as Jordan showed on 11 October; the dashboard is not in the repository) | Re-enter at the new host. Never in the repository. |
| Deploy previews | Netlify + GitHub | A preview URL on every PR; how Jordan reviews | Cloudflare Pages, Vercel and others do the same. Any move must keep this: it is the review process. |
| Domain and DNS | Not in the repository | Where cuahsi.org (or the chosen domain) points | Not known from here. |

Not Netlify, and unaffected by a move: the Nuxt build, Pagefind search (built into `.output/public`), the content, the visual baseline, `scripts/verify.sh`, and `.github/workflows/verify.yml` (GitHub Actions; its Node version should stay equal to `netlify.toml`'s).

Services the pages call from the visitor's browser or link to, which a move does not change: Google Fonts (`nuxt.config.ts`), `api.waterdata.usgs.gov`, YouTube, Mailchimp (`cuahsi.us3.list-manage.com`), JotForm, Zeffy, Constant Contact. I found no Netlify Forms (`data-netlify`) or `/.netlify/` URLs in the code.

## Before going public

1. **Indexing is off in more than one place.** `netlify.toml` sends `X-Robots-Tag: noindex, nofollow, noarchive`; the built `robots.txt` says `Disallow: /` ("indexing disabled", from the `@nuxtjs/robots` module, with `assets/robots.txt` also saying `Disallow: /`); the built home page has `<meta name="robots" content="noindex, nofollow">`. I did not trace why the module and the meta tag are set that way. Removing it touches `netlify.toml` (rule 8: Jordan decides) and probably more files, since I did not find where the other two come from (`nuxt.config.ts` sets no site, robots or noindex option). It needs a check of all three on the deploy preview and, after launch, on the live site. Missing one leaves the site hidden from search without any error.
2. **`/member-portal` has no access control.** The README says to gate it at the edge before production. Its warning dates from before the member email addresses were stripped from the build (`server/plugins/strip-rep-emails.ts`); I did not re-check what the page shows now. Decide: gate it, or remove the route (rule 8).
3. **The sitemap and canonical host.** `nuxt.config.ts` sets no site URL. I did not check what host the sitemap and robots module will use on the real domain. Check on the preview of the launch PR.
4. **Account ownership.** The Netlify team, the domain registrar and DNS should belong to CUAHSI, with at least two administrators. Not visible from the repository.
5. **Plan against traffic.** Plans cap bandwidth, build minutes and function or edge invocations. The home page calls `/api/geo` and `/api/gage` on every load, so function use grows with page views, not with the number of different pages. Compare the dashboard's current usage with the plan limits before promoting the site.
6. **`/api/gage` and its cache.** Seen on a deploy preview of the organisation's pull request on 12 October 2026: the function deploys, the key is visible to it (`x-gage-key: yes`), and an answer is stored with the lifetime the function asks for; but Netlify's edge seems to keep a separate copy per node (my guess; 1 of 11 repeat requests was a hit; adding `durable` made no visible difference), so most page loads reach the function and use the key's allowance (1000 requests an hour, from the `x-ratelimit-limit` header Jordan read on 11 October; not in the repository). Past the limit the page falls back to asking USGS directly. Another caching layer (Netlify Blobs, or a normal function with `durable`) is untested. Watch `x-ratelimit-remaining` on the key in use, and ask USGS to raise the limit if needed. The same preview showed a bug the tests could not: the CDN cached the first version's replies on the path alone and served one gage's answer for another (fixed by putting the question in the path).
7. **Node version.** Netlify and CI are on Node 20. `agent/reports/261004_node22-readiness.md` records, in its status line, Jordan's decision not to change it yet. That report says, as far as its author knew and without a source, that Node 20 reaches end of life in 2026; check Node's release schedule, and revisit before launch.
8. **Procurement.** If CUAHSI or its host institution needs a security or accessibility review, or a data-processing agreement, for a commercial host, that is outside what the repository shows.

## How to leave (outline)

1. Pick the target and say what must carry over: deploy previews on every PR, the redirects, the two functions, the header, the secret.
2. On a branch, add the target's configuration next to `netlify.toml` (do not delete `netlify.toml` yet). Rewrite `geo.ts` and `gage.ts` for the target and run `node scripts/test-gage-function.mjs` against the new gage function (the script fakes USGS, so it is a check of the code, not of the host's caching).
3. If the redirect format differs, change `scripts/parity/redirects.mjs` to write it, and update `scripts/check-redirects.mjs` and `scripts/check-links.mjs` if they read Netlify files.
4. Stand the site up at the target under a temporary address. Run the visual comparison and `verify.sh --build` against it; open the 26 routes at two widths (the 52 screenshots in `visual/README.md`), the card on `/`, and the redirects (a sample of the 337 and `/archive`).
5. Lower the DNS time to live a day ahead, move the domain, watch the card and the redirects, and keep the Netlify site up for a week as the way back.
6. Remove Netlify's files in their own PR, and fix the README, `.github/workflows/verify.yml`'s comment, `scripts/check-no-api-key.mjs`'s wording if it names Netlify, and this page.

Rule 8 applies to all of it: `netlify.toml` and any change to a URL or redirect need Jordan's word first.

## Not known (from the repository alone)

- The Netlify plan, its limits, current usage and price.
- Who owns the Netlify team, the domain and DNS, and how many administrators there are.
- Whether the dashboard has settings not in `netlify.toml` (build hooks, form detection, a different Node version; the report above could not see them either).
- Whether CUAHSI or its host institution has hosting, security or procurement requirements.
- Whether any cache can be made shared across Netlify's edge nodes for `/api/gage` (item 6: not seen working; untested alternatives).
